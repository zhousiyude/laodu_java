在 Java 中终止线程，核心是**协作式（Cooperative）** 而非强制性。理解这一点，就能明白为何 `stop()` 被废弃，而另外两种方式成为主流。下面分别介绍这三种方式，并重点对比后两者的区别。

### 三种方式速览


| 方式              | 核心机制                        | 安全性             | 能否响应阻塞             | 推荐度                 |
| :---------------- | :------------------------------ | :----------------- | :----------------------- | :--------------------- |
| **布尔标记位**    | 线程定期检查一个`volatile` 变量 | 高（协作式）       | **否**（需等待阻塞结束） | 推荐用于简单计算循环   |
| **`stop()`**      | 强行抛出`ThreadDeath` 错误      | **极低**（不安全） | 是（但以破坏性方式）     | **严禁使用**（已废弃） |
| **`interrupt()`** | 设置中断标志 + 可唤醒阻塞       | 高（协作式）       | **是**（可抛出异常唤醒） | **首选推荐**           |

---

### 方式一：布尔标记位（协作式）

这是最直观的协作方式。线程内部维护一个 `volatile` 布尔变量（`volatile` 保证了变量在多线程间的可见性），外部通过修改它来“通知”线程停止，线程在运行循环中主动检查这个标记。

**基础代码示例**

```java
public class FlagStop implements Runnable {
    private volatile boolean canceled = false; // 关键：volatile 保证可见性

    public void cancel() {
        canceled = true;
    }

    @Override
    public void run() {
        while (!canceled) {
            // 执行任务...
        }
        // 循环外的清理工作
    }
}
```

**优点**：实现简单，逻辑清晰，线程可以在退出前从容完成清理工作。
**核心缺陷**：**无法及时响应阻塞状态**。如果线程正阻塞在 `sleep()`、`wait()` 或 I/O 操作上，它根本执行不到检查 `canceled` 的代码行，必须等阻塞自然结束后才会发现标记变化。

> **进阶**：如果多个线程可能同时修改标记，可以使用 `AtomicBoolean` 来保证操作的原子性，使 `cancel()` 方法本身成为线程安全的。

---

### 方式二：`stop()`（强制终止，已废弃）

`Thread.stop()` 会强行终止线程，并导致该线程立即释放它持有的所有锁（监视器）。这听起来很“高效”，但正是问题所在。

**为什么不安全？**
它会在**任意时刻**打断线程，被强行解锁的临界区对象可能处于**不一致的中间状态**。其他线程随后访问这个“受损”对象时，程序会出现难以复现的、诡异的错误。

此外，`stop()` 抛出的 `ThreadDeath` 错误是“静默”的，默认不会打印任何警告信息，你甚至不知道程序已经被破坏了。因此，**任何情况下都不应使用 `stop()`** 。

---

### 方式三：`interrupt()`（中断机制，首选）

`interrupt()` 是 Java 设计的标准协作式中断机制。它不直接停止线程，而是**设置线程的中断标志**，并利用异常机制，弥补了布尔标记位无法响应阻塞的缺陷。

**核心行为**

- 如果线程正在 `sleep()`、`wait()`、`join()` 等可中断的阻塞调用中，`interrupt()` 会**立即触发 `InterruptedException`**，让线程从阻塞中醒来，从而有机会处理中断。
- 如果线程正在正常运行，`interrupt()` **仅设置中断标志**，线程需要像检查布尔标记一样，通过 `isInterrupted()` 来检查并响应。

**推荐的标准写法**

```java
public class InterruptDemo implements Runnable {
    @Override
    public void run() {
        // 循环条件：检查中断标志
        while (!Thread.currentThread().isInterrupted()) {
            try {
                // 可中断的阻塞操作，是响应中断的关键
                Thread.sleep(1000);
                // 执行非阻塞任务...
            } catch (InterruptedException e) {
                // 捕获到异常，说明在阻塞中被中断了
                System.out.println("在阻塞中被中断，准备退出...");
                // 关键：重新设置中断标志，让外层循环条件也能感知到
                Thread.currentThread().interrupt();
                // 在这里执行清理工作，然后退出循环
                break; 
            }
        }
        // 最终的清理工作
    }
}
```

**为什么要在 `catch` 中调用 `interrupt()`？**
因为 `InterruptedException` 抛出时，**JVM 会清除中断标志**。如果在 `catch` 块中不重新设置标志，外层循环的 `isInterrupted()` 可能无法感知到中断已经发生，导致线程无法按预期退出。

**优点**：既能处理正常循环，又能及时唤醒阻塞，是安全性和响应性结合得最好的方案。
**缺点**：需要线程代码配合（正确检查标志或捕获异常），如果线程逻辑完全忽略了中断，`interrupt()` 也无能为力。

### 总结与选择建议

- **绝对不要使用** `Thread.stop()`。
- **首选** `interrupt()` 机制，尤其是当你的线程可能涉及任何形式的阻塞操作时。
- **布尔标记位**适用于逻辑简单、纯粹的计算密集型循环，且你能确保循环足够紧凑，能频繁检查标记。但在实际工程中，`interrupt()` 因其更全面的覆盖能力，通常是更稳妥的通用选择。
- 无论使用哪种协作方式，**线程的清理工作**（关闭资源、保存状态）都应放在 `run()` 方法中循环结束后的代码块或 `finally` 块里，以保证执行。
