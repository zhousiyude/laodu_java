# Java 权限修饰符体系笔记

> 核心命题：**"权限是谁对谁而言的？"** —— 答案随层级而变。混淆层级是绝大多数困惑的根源。

---

## 一、总纲：权限发生在两个截然不同的层级上

| 层级 | 控制对象 | 可用修饰符 | 关键点 |
| :--- | :--- | :--- | :--- |
| **顶层层级** | 一个类**本身**能否被"看见" | 仅 `public` / 包私有 | 顶层类**不能**是 `private` 或 `protected` |
| **成员层级** | 类内部的字段、方法、构造器、成员内部类 | `public` / `protected` / 包私有 / `private` | 经典四选一 |

理解任何权限问题，**先问：这是顶层层级还是成员层级？** 然后才问：相对于谁？

---

## 二、成员层级的经典坐标系

这张表是全文的"地基"，回答的是：**一个成员，相对于声明它的那个类，能被哪些外部代码访问？**

| 修饰符 | 同一类内部 | 同一包内 | 跨包子类 | 任意位置 |
| :--- | :---: | :---: | :---: | :---: |
| `public` | ✓ | ✓ | ✓ | ✓ |
| `protected` | ✓ | ✓ | ✓ | ✗ |
| 包私有（默认） | ✓ | ✓ | ✗ | ✗ |
| `private` | ✓ | ✗ | ✗ | ✗ |

> ⚠️ 这张表**只对普通顶层类的成员成立**。内部类场景会叠加"边界折叠"，见第四节。

---

## 三、顶层层级：只有两种选择

顶层类的声明修饰符只有：

- `public` —— 任何包可见
- 包私有（无修饰符） —— 仅同包可见

**为什么不能 `private` / `protected`？** 因为顶层类没有"外层类"或"子类上下文"作为访问入口，`private`/`protected` 的语义在这里无处落脚。`protected` 依赖"子类"概念，而顶层类虽然可以被继承，但 `protected` 顶层类在语法上就不被允许——JLS 直接禁止。

---

## 四、内部类：双重身份与 `private` 边界折叠（重点）

成员内部类具有**双重身份**，必须拆开看。

### 4.1 身份一：作为"成员"——内部类声明上的修饰符

写在**内部类类声明上**的修饰符（`private class Inner {}`），控制的是**这个内部类本身**对外的可见性，规则与普通成员完全一致：

| 内部类声明修饰符 | 谁能访问这个内部类？ |
| :--- | :--- |
| `private` | **仅外部类内部**（含其他内部类） |
| 包私有 | 同包 |
| `protected` | 同包 + 跨包子类 |
| `public` | 任意位置（前提外部类可见） |

> 注意：`private` 内部类即使有 `public` 成员，外部世界也访问不到——类型本身不可见，成员的 `public` 失去意义。

### 4.2 身份二：作为"顶层类体的一部分"——`private` 边界折叠

**这是整个权限体系中最反直觉、最核心的一点。**

根据 **JLS §6.6.1**，`private` 成员的访问边界是：

> **"包含该成员声明的顶层类体（top level class body）"**，而非声明它的那个类本身。

因此：

- **外部类 ↔ 成员内部类**：同处一个顶层类体，`private` **互相不设防**。
  - 内部类 → 外部类：可无条件访问外部类所有成员，包括 `private`。
  - 外部类 → 内部类：可通过内部类实例访问其 `private` 成员。
- **`private` 的真正"对手"**：是**顶层类体之外的世界**，而不是外部类。

```
┌─────────────── 顶层类体（private 边界） ───────────────┐
│  Outer                    Inner                       │
│   private int a;  ←────→  private int b;             │
│     （互访无碍，同属一个边界内）                        │
└───────────────────────────────────────────────────────┘
              ↑
        private 真正阻挡的，是这里的"外部世界"
```

### 4.3 局部内部类与匿名内部类：修饰符彻底失效

在方法内定义的**局部类**和**匿名类**，其成员上的 `private` / `protected` / `public` **完全失效**。原因：能触达它们的代码，必然已经与它们同处一个顶层类体或同一个方法作用域内，修饰符失去区分意义。它们能声明的成员修饰符实际上只有"有效"的那一种语义——对外一律不可见。

### 4.4 静态内部类 vs 非静态内部类

访问规则**完全一致**（同样折叠到顶层类体），区别仅在**访问方式**：

| 类型 | 外部类访问其 `private` 静态成员 | 外部类访问其 `private` 实例成员 |
| :--- | :--- | :--- |
| 静态内部类 | `Inner.staticField` 直接访问 | 需 `new Inner().field` |
| 非静态内部类 | — | 需 `new Inner().field` |

### 4.5 实现层的缝隙：合成访问器

JVM 字节码层面**不理解"内部类"**，它看到的是两个独立类。编译器（`javac`）为了让外部类和内部类互访 `private`，会**自动生成包可见（package-private）的合成访问器方法**（如 `access$000`）。

源码：
```java
new Inner().inProp   // inProp 是 private
```
编译后等价于：
```java
Outer$Inner.access$000(new Inner())
```

**衍生后果（真实的安全缝隙）**：这个合成方法在字节码中是**包私有**的。因此，**同一个包中的其他类**理论上可以通过 `access$xxx` 方法，间接访问到本应 `private` 的成员。这是语言语义与字节码实现之间的真实裂缝。

> 💡 记忆锚点：`private` 在**语言层面**封闭顶层类体；在**字节码层面**封闭的是"类"，靠合成器打洞。

## 五、继承中的权限：只能维持或扩大，不能缩小

### 5.1 方法重写的单向约束

子类重写父类方法时，**不能降低**访问权限：

| 父类方法权限 | 子类重写时允许的权限 |
| :--- | :--- |
| `public` | 仅 `public` |
| `protected` | `protected` / `public` |
| 包私有 | 包私有 / `protected` / `public` |
| `private` | **不可重写**（同名方法只是新方法） |

**为什么不能缩小？** 里氏替换原则的权限维度：子类对象必须能替代父类对象被使用。若收紧权限，持有父类引用的代码会突然无法调用——多态契约被破坏。

### 5.2 三个容易踩的坑

1. **跨包的包私有方法不被继承**：子类中写同签名方法只是"新方法"，不构成重写，`super` 也调不到父类那个包私有方法。
2. **`private` 方法不参与继承体系**：子类同签名 `private` 方法与父类方法无任何覆盖关系。
3. **字段没有"重写"概念**：父类 `private` 字段与子类同名字段是两个独立字段，子类字段会"遮蔽"（shadow）父类字段，但父类方法内部访问的仍是父类字段。

## 六、`protected` 的精确边界（常被过度简化）

常见概括"同包 + 子类"**掩盖了关键限制**。精确规则（JLS §6.6.2）：

> 跨包访问 `protected` 成员时：
> 1. 访问代码必须位于**子类 `S` 的类体内部**；
> 2. 被访问的成员必须通过 **`S` 类型（或 `S` 的子类型）的引用**访问。

**反例**——以下代码**编译失败**：

```java
package p1;
public class A {
    protected void m() {}
}

package p2;
public class B extends A {
    void test(A a) {
        a.m();          // ❌ 编译错误！通过父类类型引用访问
    }
    void test2(B b) {
        b.m();          // ✓ 通过子类类型引用访问，OK
        this.m();       // ✓ 等价于 this（B 类型）
    }
}
```

**结论**：`protected` 的"子类可见"并不是授予"子类这个身份"，而是**授予子类类体内部的代码，且仅限于通过子类类型进行的访问**。

## 七、接口：隐式 `public` 的简化世界

接口刻意简化了权限模型：

| 接口成员 | 隐式修饰符 |
| :--- | :--- |
| 抽象方法、默认方法、静态方法 | `public`（可省略） |
| 字段（常量） | `public static final` |
| `private` 方法（Java 9+） | 仅接口内部辅助用，非对外 API |

- Java 8 之前：接口成员不允许 `private` / `protected`。
- Java 9+：允许 `private` 接口方法，但**只作为接口内部的辅助方法**，不能被实现类或外部调用。
- 接口**不能**有 `protected` 成员。

**"谁对谁而言"的答案**：接口方法对实现类和外部调用者都是 `public` 的，访问控制在这里被简化为服务于"定义契约"这一目的。

## 八、模块系统（JPMS）：叠加在 `public` 之上的第四层可见性

Java 9 的模块系统在传统四修饰符**之上**增加了一个**独立的封装层级**，它不取代 `public`/`private`，而是**在其之上加一道闸门**。

### 8.1 核心规则

> 即使一个类是 `public` 的，如果它所在的**包**没有在 `module-info.java` 中通过 `exports` 导出，**其他模块仍然无法访问它**。

```java
// module-info.java
module com.example {
    exports com.example.api;      // 只有这个包对外可见
    // com.example.internal 未导出 → 模块外完全不可见
}
```

### 8.2 `public` 的语义被条件化

| 场景 | `public` 类的实际可见性 |
| :--- | :--- |
| 所在包**被导出** | 对模块外可见（传统意义） |
| 所在包**未导出** | 仅**本模块内部**可见，模块外完全看不到 |

**重新表述"谁对谁而言"**：

> 模块下的 `public` 不再问"对全世界是否可见"，而是问"**对模块外部是否可见——取决于所在包是否被显式导出**"。

这是 Java 访问控制从"类—包"二维，扩展到"类—包—模块"三维的标志。

### 8.3 层次关系图

```
┌──────── 模块层（exports）────────┐   ← 第一道闸门
│  ┌──── 顶层层级（public/包私有）──┐│   ← 第二道闸门
│  │  ┌── 成员层级（四修饰符）──┐   ││   ← 第三道闸门
│  │  │  private/protected/... │   ││
│  │  └────────────────────────┘   ││
│  └───────────────────────────────┘│
└───────────────────────────────────┘
```

**穿过所有闸门，访问才成立。** 任何一层不通过，访问即被拒。

## 九、全局对照总表

| 场景 | 权限"对谁而言" | 关键结论 |
| :--- | :--- | :--- |
| **顶层类声明** | 其他包的代码 | 仅 `public` / 包私有 |
| **普通成员** | 相对于声明类的外部代码 | 经典四选一坐标系 |
| **内部类声明** | 外部世界对该内部类 | 同成员规则 |
| **内部类 ↔ 外部类成员** | 顶层类体之外的世界 | `private` **折叠到顶层类体**，互访无碍 |
| **局部/匿名类成员** | — | `private`/`protected`/`public` **全部失效** |
| **方法重写** | 父类方法的契约 | **只能扩不能缩**，`private` 不参与 |
| **跨包包私有方法** | — | 不继承、不可重写 |
| **`protected` 跨包** | 子类类体内部，通过子类类型引用 | **不能**通过父类类型引用访问 |
| **接口成员** | 实现类 + 外部 | 隐式 `public`（Java 9 允许 `private` 辅助） |
| **`public` 类 + 模块** | 取决于包是否被 `exports` | `public` 语义被**条件化** |

---

## 十、记忆锚点（速查）

1. **两个层级**：顶层（类本身）/ 成员（类内部成员）——先问层级。
2. **`private` 的边界是"顶层类体"，不是"类"** ——内部类互访无碍的根源。
3. **字节码层 `private` 只封闭"类"，靠合成访问器打洞** ——包内其他类可通过 `access$xxx` 间接访问，真实缝隙。
4. **继承：只能扩，不能缩；`private` 不参与；跨包包私有不继承**。
5. **`protected` 跨包 = 子类类体 + 子类类型引用**，两个条件缺一不可。
6. **接口 = 隐式 `public` 的简化世界**，Java 9 仅加了 `private` 辅助。
7. **模块层 = 叠加闸门**，`public` 不再等于"全世界可见"，而是"取决于 `exports`"。
8. **局部/匿名类 = 修饰符失效区**，因为它们已被顶层类体完全包住。

---

> **一句话收束全文**：
> **"权限是谁对谁而言的？"——随层级而变。成员层级问的是"相对于声明类的外部代码"；内部类场景下 `private` 折叠到顶层类体；继承中只能扩不能缩；接口固定为 `public`；模块层在 `public` 之上再叠一道"包导出"闸门。四修饰符 + 内部类折叠 + 继承约束 + 模块系统，构成一个分层而非平铺的体系。**
