这个说法**大体正确，但要加限定条件**：哈希桶数组长度取 **2 的整数幂**，核心收益是**加快索引计算**；它只有在配合良好的哈希扰动函数时，才有助于**让桶分布更均匀、减少冲突**。并不是“只要是 2 的幂就自动减少冲突”。

### 1. 为什么能加快散列计算？

哈希表通常要算：

```text
index = hash % n
```

如果 `n = 2^k`，那么：

```text
hash % n == hash & (n - 1)
```

因为 `n-1` 的二进制是低 `k` 位全 1，例如：

```text
n = 16      -> 10000
n - 1 = 15  -> 01111
hash & 15   -> 只保留 hash 的低 4 位
```

位运算 `&` 比取模 `%` 快很多。所以 Java HashMap 等实现用：

```java
index = (n - 1) & hash;
```

这就是“加快散列计算”的主要原因。

### 2. 为什么说能减少散列冲突？

更准确地说，是**在哈希值分布较均匀时，2 的幂配合位掩码可以让桶索引分布更均匀**。

例如 `n = 16`，`n-1 = 15`，索引只看 hash 的低 4 位：

```text
index = hash & 15
```

如果 hash 的低位分布均匀，那么 16 个桶被选中的概率就接近均匀，冲突自然少。

但这里有个问题：如果 hash 函数不好，低位规律性强，比如很多 hash 的低位都一样，那么 `hash & (n-1)` 会集中到少数桶，冲突反而严重。所以 HashMap 会先做扰动：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

也就是把高 16 位异或到低 16 位，让高位也参与桶索引计算，从而改善低位分布，减少冲突。

### 3. 扩容时也有利于减少冲突和迁移

当容量是 2 的幂时，扩容为原来的 2 倍，即：

```text
oldCap = 2^k
newCap = 2^(k+1)
```

元素的新索引只有两种可能：

```text
原索引
原索引 + oldCap
```

这是因为多看了 hash 的某一位。这样 rehash 时不需要重新完整取模，只需要判断这一位是 0 还是 1，迁移效率高，也有利于保持分布均匀。

### 4. 需要纠正的表述

更严谨的说法是：

> 哈希桶数组长度取 2 的整数幂，主要是为了用 `hash & (n-1)` 代替 `hash % n`，加快索引计算；同时配合哈希扰动函数，使低位分布更均匀，从而减少冲突；扩容时也便于元素重新分布。

而不是简单说：

> 只要是 2 的整数幂，就一定能减少冲突。

因为如果 hash 函数质量差，2 的幂容量反而可能放大低位冲突。**2 的幂是“计算快 + 便于均匀分布 + 便于扩容”的组合优化，冲突减少依赖于哈希函数和扰动机制。**
